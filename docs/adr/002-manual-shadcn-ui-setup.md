# 002. shadcn/ui wired up by hand instead of via the CLI

## Context

CLAUDE.md specifies shadcn/ui as the UI component library. The standard setup
path is `npx shadcn@latest init`, which fetches the project's chosen style,
base color, and component registry from `ui.shadcn.com` over the network.

In the environment this project was built in, outbound requests to
`ui.shadcn.com` are blocked by the sandbox's network policy (confirmed via
repeated `init` attempts, all failing with `403`/"Request was cancelled" at
the registry fetch step, and via a direct `curl` returning a `CONNECT
tunnel failed, response 403`). This is specific to that build environment,
not a shadcn/ui or project problem.

## Decision

Reproduce what `shadcn init` would have generated, by hand:

- `components.json` — written manually, matching the CLI's own schema
  (`style: "new-york"`, Radix primitives, `src/components/ui` alias).
- `src/lib/utils.ts` — the standard `cn()` helper (`clsx` + `tailwind-merge`).
- `src/components/ui/{button,badge,input,card}.tsx` — the canonical shadcn
  component source for each primitive, using `class-variance-authority` for
  variants, adapted to this project's color tokens.

The color tokens themselves (`--primary`, `--secondary`, `--accent`,
`--muted`, `--border`, `--ring`, ...) are defined directly in
`src/app/globals.css` from CLAUDE.md's palette, rather than generated by the
CLI from a "base color" preset — this project has its own brand palette, not
a shadcn default one.

## Alternatives Considered

- **Retry `shadcn init` from a different network context.** Not available in
  this build environment. Documented here so that a future contributor
  working from an unrestricted network can run the CLI normally (e.g. for
  `shadcn add <component>`) without needing to know this history — the
  files it would touch already exist and match its expected shape.
- **Skip shadcn/ui, hand-roll all components independently.** Rejected: it
  would silently diverge from CLAUDE.md's stated stack and from the
  component API (`variant`, `size`, `asChild`) that future components and
  any real `shadcn add` usage would expect.

## Consequences

- `npx shadcn add <component>` should work normally in an environment with
  network access, since `components.json` is already in place and matches
  what the CLI generates.
- Any new shadcn primitive added by hand (as Dialog, Tabs, etc. are needed by
  later pages) should follow the same pattern: canonical component source,
  adapted only to this project's existing color tokens — not restyled.
